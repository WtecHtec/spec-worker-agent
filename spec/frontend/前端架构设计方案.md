# Antigravity Agent - 前端架构设计方案

> **版本**：v1.0.0 (生产就绪)  
> **技术栈**：Next.js 14 (App Router) + TypeScript + Tailwind CSS + Zustand + Framer Motion + React Markdown  
> **核心定位**：高可靠、企业级 Agent 任务流实时调度与人机协同交互客户端。

---

## 一、架构设计总览

前端采用 **「视图层（React UI） - 状态层（Zustand Stores） - 调度层（Custom Hooks） - 网络层（API & SSE）」** 的单向数据流整洁分层架构：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            1. 视图展现层 (UI Layer)                         │
│  - Sidebar: 会话列表、实时搜索过滤、用户卡片                                │
│  - ChatWindow: 历史消息流、智能节流吸底滚动                                 │
│  - MessageItem: USER 气泡 / AGENT 卡片                                      │
│  - StepContainer: 步骤流水容器 (Thinking / Tools / Results / Final)         │
│  - HitlStep: 人机协同决策交互卡片 (Choice / Text Input)                     │
│  - ChatInput: 快捷提示词、自适应高度输入框、即时任务终止按钮                 │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 读取 / 触发
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                        2. 全局状态层 (Zustand Stores)                       │
│  - useAuthStore: Token 持久化、用户信息、401 自动失效监听                   │
│  - useSessionStore: 会话列表、当前活跃会话、消息流转                        │
│  - useTaskStore: 按 Task ID 严格隔离的步骤字典 Map、活跃 HITL 状态          │
│  - useToastStore: 409 互斥冲突 / 429 配额拦截浮动通知                        │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 驱动
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                          3. 核心调度层 (Custom Hooks)                       │
│  - useTaskStream: SSE 连接生命周期管理、指数退避重连、游标增量续传           │
│  - useTypewriter: rAF 逐帧帧预算渲染、动态缓冲防积压加速打字机              │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 请求 / 监听
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                        4. 网络与协议层 (Network & API)                      │
│  - REST API Client: Token 注入、401 事件派发、429 Retry-After 解析           │
│  - EventSource Agent: SSE 实时事件流监听 (携带 ?token= 认证参数)            │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 二、端到端通信与交互协议规范

### 1. RESTful API 交互接口

| 模块 | 方法 | 路径 | 功能说明 | 核心交互逻辑 |
|---|---|---|---|---|
| **Auth** | `POST` | `/auth/login` | 用户登录 | 获取 JWT Token，持久化到 LocalStorage |
| **Sessions** | `GET` | `/sessions` | 会话列表 | 获取当前用户的历史会话列表（按时间倒序） |
| **Sessions** | `POST` | `/sessions` | 创建会话 | 初始化新会话 |
| **Messages** | `GET` | `/sessions/{id}/messages` | 消息历史 | 拉取当前会话的全量消息记录 |
| **Messages** | `POST` | `/sessions/{id}/messages` | 发送消息 | 写入 USER 消息与 AGENT 占位消息，生成并入队 Task，返回 `task_id` |
| **Tasks** | `GET` | `/tasks/{id}/steps` | 历史步骤 | 针对断点会话按需拉取已落库的步骤明细 |
| **Tasks** | `POST` | `/tasks/{id}/cancel` | 终止任务 | 立即将任务标记为 `CANCELLED`，释放 Worker 与输入框 |
| **HITL** | `GET` | `/tasks/{id}/hitl/pending` | 查询待审批 | 获取当前任务待处理的人机协同审批单 |
| **HITL** | `POST` | `/tasks/{id}/hitl/{id}/respond` | 提交决策 | 用户提交审批选项/文本，唤醒任务从断点继续执行 |

### 2. SSE 实时推流协议规范

客户端通过 `EventSource` 建立长连接：
```http
GET /tasks/{task_id}/stream?from_step={cursor}&token={jwt_token}
Content-Type: text/event-stream
```

#### 推送事件类型（Event Types）

```
1. new_step (步骤推送)
event: new_step
data: {"task_id":"...","step_index":1,"step_type":"THINKING","content":{"text":"..."},"created_at":"..."}

2. hitl_created (触发人机协同审批)
event: hitl_created
data: {"task_id":"...","hitl_id":"...","question":"扫描发现 500 条异常，如何处理？","options":[{"value":"skip","label":"跳过"}]}

3. task_completed (任务圆满完成)
event: task_completed
data: {"task_id":"...","result":{"summary":"...","total_steps":6}}

4. task_failed (任务执行失败)
event: task_failed
data: {"task_id":"...","error":"数据库连接超时"}

5. task_cancelled (任务被主动取消)
event: task_cancelled
data: {"task_id":"..."}

6. ping (心跳保活)
event: ping
data: {}
```

## 三、四大核心机制与设计方案

### 机制一：基于 `requestAnimationFrame` (rAF) 的高性能流式渲染

#### 痛点与挑战
传统使用 `setInterval` 或每收到 SSE 字符立即 `setState` 的方案，在高频推流下会导致 React 每秒触发 100+ 次重绘，导致浏览器主线程卡死、掉帧和输入框打字卡顿。

#### 核心实现 (`useTypewriter`)
1. **屏幕刷新率对齐**：使用 `requestAnimationFrame` 驱动逐帧消费，渲染帧率严格锁定 60FPS / 120FPS。
2. **动态自适应防积压加速**：
   - 内部维护 `targetTextRef` 目标缓冲池；
   - 当积压字符较少时：每帧输出 1 个字符（平滑优雅的打字动画）；
   - 当后端大段文本突发推流（积压 > 40~100 字符）时：单帧步长自适应提升至 3~6 字符，**确保界面视觉体验丝滑，同时绝不滞后于后端实际进度**。
3. **历史数据瞬时直出**：仅对当前正在推流的活跃步骤启用 rAF 打字机；页面刷新或回看历史会话时直接瞬时展示完整文本。

---

### 机制二：无重复增量断点续传与游标管理 (`from_step`)

#### 游标流转设计
1. **客户端本地维护游标**：
   - 前端维护 `latestStepRef.current`；
   - 每收到一个 `new_step` 事件，自动将游标更新为 `Math.max(latestStepRef.current, data.step_index)`。
2. **连接建立与重试**：
   - 建立连接时仅在 `taskId` 切换时初始化一次；
   - 遇到网络波动触发指数退避重连（`1s → 2s → 4s → 8s → 15s`）时，自动携带 `from_step=${latestStepRef.current}`；
   - 服务端优先从 PostgreSQL 补齐断网期间生成的历史步骤，随后无缝切入 Redis Pub/Sub 实时推流，**做到弱网环境下 0 丢步、0 重复**。

### 机制三：人机协同 (HITL) 决策状态机闭环

```
                         【Worker 遇到高危/歧义操作】
                                      │
                                      ▼
                        广播 hitl_created 事件到 SSE
                                      │
                                      ▼
                      前端渲染专属 <HitlStep /> 交互卡片
                    (支持单选 Choice / 自由文本 Text Input)
                                      │
                         【用户点击并提交决策】
                                      │
                                      ▼
                  POST /tasks/{taskId}/hitl/{hitlId}/respond
                                      │
                     ┌────────────────┴────────────────┐
                     ▼                                 ▼
           【前端即时反馈】                   【服务端异步唤醒】
     - 卡片更新为「已确认」锁定态      - hitl_requests 更新为 RESOLVED
     - 弹出 Toast 提示               - Task 重新推入 Redis Stream
     - 保持监听后续实时步骤           - Worker 领任务从断点继续执行
```

---

### 机制四：多会话状态隔离与连接生命周期

1. **状态存储严格按 Task ID 隔离**：
   ```typescript
   interface TaskState {
     stepsByTask: Record<string, TaskStep[]>;       // key: taskId
     activeHitlByTask: Record<string, HitlRequest>; // key: taskId
     taskStatus: Record<string, string>;            // key: taskId
   }
   ```
   多个会话同时执行任务时，数据严格通过 `taskId` 检索，杜绝跨会话数据污染。
2. **会话切换连接生命周期**：
   - 切换离开会话时：触发 `useTaskStream` 的 cleanup 函数，调用 `es.close()` 释放当前视图的长连接资源；
   - 后台任务状态：服务端 Worker 持续独立运行并落库；
   - 重新切回该会话时：进入页面自动检测最后一条消息状态，发起带 `from_step` 的连接，1毫秒内补全期间在后台产生的所有步骤。

## 四、异常处理与防御性设计

| 场景 | 状态码 / 现象 | 前端防御与处理方案 |
|---|---|---|
| **登录态失效** | `401 Unauthorized` | 拦截器清除本地 Token，派发 `agent_auth_expired` 事件弹出登录弹窗，不刷新页面。 |
| **单会话并发冲突** | `409 Conflict` | 弹出 Toast 提示：“当前会话已有任务正在执行中，请等待完成或先终止当前任务”。 |
| **并发任务配额超限** | `429 Quota Exceeded` | 弹出 Toast 提示：“已达到单用户最大并发任务数限制（3个），请等待其他任务完成”。 |
| **请求速率限流** | `429 Rate Limit` | 解析响应头 `Retry-After`，提示用户在 N 秒后重试。 |
| **主动终止任务** | 点击「终止」按钮 | 调用 `cancelTask` 接口并在本地**即时更新**消息为 `CANCELLED`，释放输入框，不依赖网络回执延迟。 |
| **历史会话首屏加载** | 包含 20+ 轮对话 | 历史已完成消息直接渲染静态文本（0 额外步骤请求），首屏秒开。 |
