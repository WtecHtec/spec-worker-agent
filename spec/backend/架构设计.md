# Agent 系统服务端技术架构设计

> 架构风格：整洁架构（Clean Architecture）+ 领域驱动设计（DDD）
> 核心原则：依赖方向永远向内，领域层不依赖任何外部框架

---

## 一、层级总览

```
┌─────────────────────────────────────────────────────────┐
│                    接口层 Interface Layer                 │
│         HTTP Router / SSE Handler / Middleware           │
└───────────────────────┬─────────────────────────────────┘
                        │ 调用
┌───────────────────────▼─────────────────────────────────┐
│                   应用层 Application Layer                │
│    用例编排（Use Cases）/ 事件调度 / DTO 转换             │
└──────────┬──────────────────────────────┬───────────────┘
           │ 调用                          │ 调用
┌──────────▼──────────┐      ┌────────────▼───────────────┐
│   领域层             │      │   基础设施层                 │
│   Domain Layer      │      │   Infrastructure Layer      │
│                     │      │                             │
│  实体 / 值对象       │      │  PostgreSQL 仓储实现         │
│  领域服务            │◄─────│  Redis 适配器               │
│  仓储接口（抽象）    │      │  消息队列实现               │
│  领域事件            │      │  外部服务（LLM / Mock）      │
└─────────────────────┘      └─────────────────────────────┘
```

**依赖规则**：
- 接口层 → 应用层（单向）
- 应用层 → 领域层（单向）
- 基础设施层 → 领域层（实现领域层定义的接口）
- 领域层不依赖任何人

## 二、领域层 Domain Layer

> 系统的核心，不含任何框架代码，只有业务规则

### 2.1 核心实体（Entity）

```
User（用户）
├── id
├── plan（free / pro / enterprise）
├── maxConcurrentTasks
├── monthlyTokenQuota
└── 领域行为：
    canCreateTask() → 检查是否超过并发限制
    hasQuota()      → 检查 Token 配额

Session（会话）
├── id
├── userId
├── agentConfig
└── 领域行为：
    addMessage()    → 追加消息，更新统计
    archive()       → 归档会话

Message（消息）
├── id
├── sessionId
├── role（USER / AGENT / SYSTEM）
├── contentType
├── content
├── taskId（可选）
└── 领域行为：
    markStreaming() → 状态变为 streaming
    complete()      → 流式完成，写入完整内容
    attachTask()    → 绑定异步任务

Task（任务）—— 最核心的实体
├── id
├── userId / sessionId / triggerMessageId
├── status（状态机）
├── priority
├── workerId / workerHeartbeat
└── 领域行为：
    start(workerId)     → PENDING → RUNNING，记录 workerId
    complete(result)    → RUNNING → COMPLETED
    fail(error)         → RUNNING → FAILED
    suspend()           → RUNNING → PAUSED（优雅退出）
    waitForHuman()      → RUNNING → WAITING_HUMAN
    resume()            → WAITING_HUMAN → PENDING（重新入队）
    isHeartbeatExpired()→ 判断 Worker 心跳是否超时

TaskStep（步骤）
├── taskId
├── stepIndex
├── type（THINKING / TOOL_CALL / TOOL_RESULT / HITL_REQUEST / FINAL）
└── content（JSONB）

HitlRequest（人工介入）
├── taskId / stepIndex
├── type（choice / text_input / file_upload / form）
├── question / options
├── status（PENDING / RESOLVED / EXPIRED）
├── expiresAt
└── 领域行为：
    resolve(decision) → PENDING → RESOLVED
    expire()          → PENDING → EXPIRED
    isExpired()       → 判断是否超时
```

---

### 2.2 值对象（Value Object）

```
AgentConfig（不可变）
├── model（"gpt-4o" / "claude-3-5" / "mock"）
├── systemPrompt
└── tools（工具列表）

TaskInput（不可变）
├── type（"text" / "file"）
└── content

StepContent（不可变，按 type 区分结构）
├── ThinkingContent   { text }
├── ToolCallContent   { toolName, arguments, idempotencyKey }
├── ToolResultContent { toolName, output, durationMs }
└── FinalContent      { text }

Checkpoint（不可变快照）
├── lastCompletedStep
├── version（乐观锁）
├── recentMessages
├── contextSummary
├── taskVariables
└── completedToolCalls（幂等记录）
```

---

### 2.3 领域服务（Domain Service）

> 跨实体的业务规则，不适合放在单个实体里

```
TaskSchedulerService（任务调度规则）
├── canEnqueue(user)
│     → 检查用户并发数 + 配额，决定是否允许入队
└── assignPriority(user, input)
      → 根据用户 plan 和输入内容计算优先级

CheckpointService（断点管理）
├── buildContext(checkpoint)
│     → 将 checkpoint 重建为 LLM 上下文
├── shouldCompress(checkpoint)
│     → 判断上下文是否需要摘要压缩
└── compress(checkpoint, llmSummary)
      → 生成新的压缩后 checkpoint

HitlDecisionService（HITL 决策处理）
└── applyDecision(hitlRequest, task, decision)
      → 验证决策合法性，更新 hitlRequest 状态，触发任务恢复
```

---

### 2.4 仓储接口（Repository Interface）

> 领域层定义接口，基础设施层负责实现。领域层完全不知道底层是 PostgreSQL 还是别的。

```
ITaskRepository
├── findById(taskId) → Task
├── findByUser(userId, filter) → Task[]
├── findZombieTasks(heartbeatBefore) → Task[]（僵尸任务扫描）
├── save(task) → void
└── updateStatus(taskId, status, extra) → void

ISessionRepository
├── findById(sessionId) → Session
├── findByUser(userId) → Session[]
└── save(session) → void

IMessageRepository
├── findBySession(sessionId, afterSeq) → Message[]
├── findByTaskId(taskId) → Message
├── save(message) → void
└── updateContent(messageId, content) → void

ITaskStepRepository
├── findByTask(taskId, afterIndex) → TaskStep[]
├── save(step) → void（幂等：冲突时忽略）
└── countByTask(taskId) → number

ICheckpointRepository
├── findByTask(taskId) → Checkpoint
├── save(checkpoint, expectedVersion) → boolean（乐观锁，版本不对返回 false）
└── delete(taskId) → void

IHitlRepository
├── findById(hitlId) → HitlRequest
├── findPendingByTask(taskId) → HitlRequest
├── findExpired(before) → HitlRequest[]
└── save(hitlRequest) → void
```

### 2.5 领域事件（Domain Event）

> 用于层间解耦，发生了什么 → 通知订阅者

```
TaskCreated       { taskId, userId, sessionId }
TaskStarted       { taskId, workerId }
TaskCompleted     { taskId, result }
TaskFailed        { taskId, error }

HitlRequested     { taskId, hitlRequestId }
HitlResolved      { taskId, hitlRequestId, decision }
HeartbeatExpired  { taskId }（监控服务发出）
```

## 三、应用层 Application Layer

> 编排领域对象，实现具体用例，不含业务规则本身

### 3.1 模块划分

```
application/
├── session/          会话模块
├── message/          消息模块
├── task/             任务调度模块
├── worker/           Worker 执行模块
└── hitl/             人工介入模块
```

---

### 3.2 会话模块（Session）

```
用例：
  CreateSessionUseCase
    输入：userId, agentConfig（可选）
    流程：创建 Session 实体 → 持久化 → 返回 sessionId

  ListSessionsUseCase
    输入：userId
    流程：查仓储 → 返回会话列表（含最后一条消息预览）

  GetSessionMessagesUseCase
    输入：sessionId, afterSeq（分页）
    流程：验证权限 → 查消息列表 → 返回 DTO
```

---

### 3.3 消息 & 任务触发模块（Message）

> 最核心的用例：用户发消息后发生什么

```
SendMessageUseCase（核心入口）
  输入：sessionId, userId, content

  流程：
    1. 验证用户有权访问该 session
    2. 检查用户配额：user.canCreateTask()
    3. 写入 USER 消息
    4. 写入 AGENT 占位消息（task_reference, status=streaming）
    5. 创建 Task 实体（PENDING）
    6. 写入 Checkpoint（初始空状态）
    7. 更新 AGENT 消息绑定 task_id
    8. 发布领域事件 TaskCreated
    9. 返回 { messageId, taskId }

  注意：步骤 3-8 应在同一个数据库事务内完成
        保证"消息存在"和"任务存在"的原子性
```

---

### 3.4 任务调度模块（Task Dispatch）

```
EnqueueTaskUseCase
  监听 TaskCreated 事件 → 推入 Redis Stream

  流程：
    1. 从事件拿到 taskId
    2. 读取 task 的 priority
    3. XADD task_queue { taskId, priority, resumeFromStep: 0 }

ResumeTaskUseCase（HITL 响应后调用）
  输入：taskId
  流程：
    1. 读取 Checkpoint 的 lastCompletedStep
    2. XADD task_queue { taskId, resumeFromStep: N }
    3. UPDATE tasks SET status=PENDING

RecoverZombieTasksUseCase（监控服务定时调用）
  流程：
    1. 查找心跳超时的 RUNNING 任务
    2. 验证对应 Redis 锁是否还存在
    3. 锁已消失 → 任务视为崩溃 → 重新入队
    4. 发送告警通知（可选）
```

---

### 3.5 Worker 执行模块（Worker）

> Worker 是独立进程，但其内部逻辑也属于应用层

```
ExecuteTaskUseCase（Worker 的主循环）
  输入：从队列取到的 taskMessage

  流程：
    1. 获取分布式锁（失败则放弃，任务已被其他 Worker 处理）
    2. 加载 Checkpoint，重建执行上下文
    3. 更新 Task 状态为 RUNNING
    4. 进入执行循环：
       a. 调用 AgentExecutor（见下）产出下一步
       b. 写入 TaskStep（幂等）
       c. 更新 Checkpoint（乐观锁，失败则退出）
       d. 发布领域事件 StepRecorded
       e. 心跳续期
       f. 检查是否收到退出信号（优雅关闭）
    5. 遇到 HITL → 写 HitlRequest → 更新状态 → 退出循环
    6. 完成 → 写结果 → 更新任务和消息 → ACK 队列

AgentExecutor（执行策略接口）
  ├── MockAgentExecutor   → 读 JSON 文件，按 delay_ms 等待后产出步骤
  └── LlmAgentExecutor    → 调 LLM API，流式解析工具调用和思考过程

  两者实现同一接口，Worker 代码完全不知道用的哪种
  通过配置文件或环境变量切换：AGENT_MODE=mock / llm
```

---

### 3.6 HITL 模块（Human-in-the-Loop）

```
GetPendingHitlUseCase
  输入：taskId
  输出：当前待响应的 HitlRequest（若有）

RespondHitlUseCase
  输入：hitlRequestId, userId, decision
  流程：
    1. 验证 hitlRequest 属于该用户的任务
    2. 验证 status = PENDING 且未超时
    3. 调用 HitlDecisionService.applyDecision()
    4. 更新 HitlRequest 状态
    5. 发布 HitlResolved 事件
    6. 触发 ResumeTaskUseCase → 任务重新入队

ExpireHitlUseCase（定时任务调用，每分钟）
  流程：
    1. 查找已超时的 PENDING HitlRequest
    2. 按 defaultAction 处理：
       cancel  → 任务直接 FAILED
       proceed → 用默认选项恢复任务
```

## 四、基础设施层 Infrastructure Layer

> 实现领域层定义的所有接口，处理所有"脏活"

### 4.1 数据库仓储实现

```
PostgresTaskRepository（实现 ITaskRepository）
  save(task)：
    → 检测是新增还是更新（有无 id）
    → INSERT ... ON CONFLICT UPDATE（幂等写入）

  findZombieTasks(heartbeatBefore)：
    → SELECT WHERE status=RUNNING AND worker_heartbeat < ?
    → 加行锁 FOR UPDATE SKIP LOCKED（防并发重复处理）

PostgresCheckpointRepository（实现 ICheckpointRepository）
  save(checkpoint, expectedVersion)：
    → UPDATE ... WHERE version = expectedVersion
    → 检查影响行数：0 行 → 版本冲突 → 返回 false
    → 应用层拿到 false 后主动退出 Worker 循环
```

---

### 4.2 Redis 适配器

```
RedisTaskQueue（任务队列）
├── enqueue(taskId, priority, resumeFromStep)
│     → XADD task_queue MAXLEN ~ 10000 * ...
├── consume(workerId, count)
│     → XREADGROUP GROUP workers {workerId} COUNT {count} BLOCK 5000
└── ack(messageId)
      → XACK task_queue workers {messageId}

RedisLockAdapter（分布式锁）
├── acquire(taskId, workerId, ttlSeconds) → boolean
│     → SET task_lock:{taskId} {workerId} NX EX {ttl}
├── renew(taskId, workerId, ttlSeconds) → boolean
│     → GET 验证 workerId → EXPIRE 续期
└── release(taskId, workerId)
      → Lua 脚本：GET 验证 → DEL（原子操作）

RedisPubSubAdapter（实时通知）
└── publish(taskId, event)
      → PUBLISH task:{taskId} {JSON.stringify(event)}
```

---

### 4.3 Agent 执行器实现

```
MockAgentExecutor
├── 根据 task.input 匹配 mock 文件（关键词匹配 or 固定场景）
├── 读取 steps.json
├── 按 step_index 顺序逐步产出
├── 按 delay_ms 模拟真实耗时
└── 遇到 wait_for_human=true → 产出 HITL 步骤

LlmAgentExecutor（占位，后续接入）
├── 将 Checkpoint 重建为 LLM messages
├── 调用 LLM API（流式）
├── 解析 tool_call / thinking / final
└── 每产出一个完整步骤，交给 Worker 处理
```

---

### 4.4 SSE 推送服务

```
SsePublisher（基础设施层提供）

职责：
  订阅 Redis Pub/Sub → 接收 StepRecorded 事件
  查询 PostgreSQL 获取 step 详细内容
  推送给对应 task 的 SSE 订阅者

连接管理：
  SseConnectionRegistry（内存 Map）
  {
    task_abc-123 → [connection1, connection2]  ← 同一任务可多窗口订阅
  }

重连处理（from_step 参数）：
  新连接建立时：
    1. 查 DB 补发 step_index > from_step 的历史步骤
    2. 注册到 ConnectionRegistry
    3. 开始接收实时推送
```

## 五、接口层 Interface Layer

### 5.1 路由结构

```
HTTP Routes：

会话
  POST   /sessions                    → CreateSessionUseCase
  GET    /sessions                    → ListSessionsUseCase
  GET    /sessions/:id/messages       → GetSessionMessagesUseCase

消息 & 任务触发
  POST   /sessions/:id/messages       → SendMessageUseCase

任务
  GET    /tasks/:id                   → 查任务状态
  DELETE /tasks/:id                   → 取消任务
  GET    /tasks/:id/steps             → 查步骤列表（用于重连时拉历史）
  GET    /tasks/:id/stream            → SSE 连接（query: from_step）

HITL
  GET    /tasks/:id/hitl/pending      → GetPendingHitlUseCase
  POST   /tasks/:id/hitl/:hitlId/respond → RespondHitlUseCase
```

---

### 5.2 中间件栈

```
请求进来的处理顺序：

1. RequestLogger      → 记录请求日志
2. AuthMiddleware     → 验证 JWT / Session Token，注入 userId
3. RateLimiter        → 按 userId 限流（Redis 计数器）
4. InputValidator     → 请求体格式校验
5. ErrorHandler       → 统一错误处理，转换为标准错误响应
```

---

### 5.3 统一错误处理

```
领域层抛出领域异常（不含 HTTP 概念）：
  TaskNotFoundException
  QuotaExceededException
  HitlAlreadyResolvedException
  CheckpointConflictException

接口层的 ErrorHandler 统一转换：
  TaskNotFoundException       → 404
  QuotaExceededException      → 429（附带 retryAfter）
  HitlAlreadyResolvedException→ 409
  CheckpointConflictException → 500（记录告警）
  未知异常                    → 500（不暴露内部细节）
```

## 七、两个进程的职责边界

```
┌─────────────────────────────────┐   ┌─────────────────────────────────┐
│       API Server 进程            │   │        Worker 进程               │
│                                 │   │                                 │
│ 接口层（路由 / 中间件 / SSE）    │   │ 应用层（ExecuteTaskUseCase）     │
│ 应用层（会话 / 消息 / HITL 用例）│   │ 领域层（Task / Step / Checkpoint）│
│ 领域层                          │   │ 基础设施层（DB / Redis / Executor）│
│ 基础设施层（DB / Redis）         │   │                                 │
│                                 │   │ 独立部署，可多实例               │
│ 面向用户请求，低延迟优先          │   │ 面向任务执行，吞吐量优先         │
└─────────────────────────────────┘   └─────────────────────────────────┘
         共享：PostgreSQL + Redis
         通信：Redis Stream（队列）+ Redis Pub/Sub（事件）
```


整体结构

```
┌──────────────────────────────────────────────────────┐
│                    前端浏览器                          │
│  创建任务 → POST /tasks → 拿到 task_id               │
│  连接推送 → GET /tasks/{id}/stream（SSE）             │
│  重新打开 → 同上，服务端自动补历史                     │
└──────────────────────┬───────────────────────────────┘
                       │
┌──────────────────────▼───────────────────────────────┐
│                   API Server                          │
│  接收请求，写任务到 PostgreSQL，推任务到 Redis Queue   │
│  SSE Handler：订阅 Redis Pub/Sub，有消息就推前端       │
└────────┬─────────────────────────┬────────────────────┘
         │                         │
┌────────▼──────────┐   ┌──────────▼────────────────────┐
│   Redis           │   │      PostgreSQL                │
│                   │   │                                │
│  Queue（任务队列）│   │  tasks（任务主表）              │
│  Pub/Sub（通知）  │   │  task_steps（步骤流水）         │
│  Lock（分布式锁） │   │  hitl_requests（人工确认）      │
│                   │   │  checkpoints（断点续传）        │
└────────┬──────────┘   └───────────────────────────────┘
         │
┌────────▼──────────────────────────────────────────────┐
│                    Worker                              │
│  从 Redis Queue 取任务                                 │
│  执行 Agent 逻辑（调 LLM、调工具）                    │
│  每步完成：INSERT task_steps + PUBLISH Redis          │
│  遇到 HITL：写 hitl_requests，更新状态，Worker 退出   │
│  完成/失败：更新 tasks 状态                           │
└───────────────────────────────────────────────────────┘

```
