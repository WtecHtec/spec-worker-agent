# 服务端功能优先级排序

> 原则：优先打通核心链路（用户发消息 → 任务执行 → 前端可见），再逐步加固可靠性

---

## P0｜核心链路跑通（第一阶段）

> 目标：用户能发消息，Worker 能跑 Mock，前端能看到步骤

### 1. 数据库初始化
```
- 建库建表（users / sessions / messages / tasks / task_steps / task_checkpoints）
- Alembic 初始化，生成第一个 migration
- 本地开发环境验证表结构
```

### 2. 用户鉴权（最小可用版本）
```
- POST /auth/register（邮箱 + 密码注册）
- POST /auth/login（返回 JWT Token）
- AuthMiddleware（解析 JWT，注入 user_id 到请求上下文）
- 不做第三方 OAuth，先跑通流程
```

### 3. 会话管理
```
- POST /sessions（创建会话）
- GET /sessions（获取当前用户的会话列表）
- GET /sessions/{id}/messages（获取会话消息列表）
```

### 4. 发消息 & 创建任务（最核心用例）
```
- POST /sessions/{id}/messages
  → 写入 USER 消息
  → 创建 Task（PENDING）
  → 写入 AGENT 占位消息（task_reference）
  → 写入初始 Checkpoint
  → 推入 Redis Stream
  → 返回 { task_id, message_id }
```

### 5. Worker 基础执行循环（Mock 模式）
```
- Worker 进程启动，从 Redis Stream 消费任务
- MockAgentExecutor：读取对应 mock JSON 文件
- 按 step_index 顺序执行，按 delay_ms 模拟耗时
- 每步：INSERT task_steps（幂等）+ PUBLISH Redis
- 任务完成：UPDATE tasks(COMPLETED) + UPDATE messages(task_status=COMPLETED)
- XACK 确认消费
```

### 6. SSE 基础推送
```
- GET /tasks/{id}/stream（建立 SSE 连接）
- 订阅 Redis Pub/Sub（task:{task_id}）
- 收到通知 → 查 task_steps → 推送给前端
- ping 事件（每 30s，防连接超时）
```

### 7. Mock 文件结构
```
- 设计 steps.json 格式（包含 delay_ms、type、content）
- 准备 2-3 个演示场景的 mock 文件
- WorkerMock 根据输入关键词匹配文件
```

**P0 完成标志**：
```
✅ 用户登录 → 创建会话 → 发消息 → 任务入队
✅ Worker 读 Mock 文件，逐步执行
✅ 前端 SSE 实时收到步骤，可以渲染
✅ 整条链路端到端跑通
```

## P1｜核心功能闭合（第二阶段）

> 目标：断点续传、HITL、任务取消，功能完整可用

### 8. 断点续传（Checkpoint 完整实现）
```
- Checkpoint 保存：每步完成后更新（last_completed_step、context_snapshot）
- Worker 启动时加载 Checkpoint，从 resume_from_step 开始执行
- 乐观锁写入（version 字段），写入失败 Worker 主动退出
- 幂等 key 记录，避免工具副作用重复执行
```

### 9. SSE 重连补历史
```
- GET /tasks/{id}/stream?from_step=N
- 服务端：先查 DB 补发 step_index > N 的已有步骤
- 再切换为实时监听
- 前端 step_index 去重保障
```

### 10. 任务状态查询
```
- GET /tasks/{id}（查任务状态、进度）
- GET /tasks/{id}/steps?after_step=N（拉取历史步骤，用于重连）
```

### 11. HITL 完整流程
```
- Mock 场景支持 wait_for_human=true 的步骤
- Worker 遇到 HITL：
    INSERT hitl_requests
    UPDATE tasks(WAITING_HUMAN)
    PUBLISH hitl_created 事件
    Worker 退出（释放资源）
- GET /tasks/{id}/hitl/pending（查当前待确认请求）
- POST /tasks/{id}/hitl/{hitlId}/respond（用户提交响应）
    → 更新 hitl_requests(RESOLVED)
    → 任务重新入队（携带 resume_from_step）
    → UPDATE tasks(PENDING)
```

### 12. 任务取消
```
- DELETE /tasks/{id}
  → 检查任务状态（PENDING/RUNNING/WAITING_HUMAN 可取消）
  → UPDATE tasks(CANCELLED)
  → Worker 心跳时检测到 CANCELLED → 主动退出循环
```

**P1 完成标志**：
```
✅ 关闭页面重新打开，历史步骤完整恢复
✅ HITL 卡片展示 → 用户响应 → 任务继续
✅ 用户可以取消进行中的任务
✅ Mock 场景覆盖：正常完成 / HITL / 失败 / 取消
```

## P2｜可靠性保障（第三阶段）

> 目标：系统在异常情况下不丢任务，Worker 崩溃自动恢复

### 13. 分布式锁
```
- Worker 取任务前：SET task_lock:{id} {worker_id} NX EX 60
- 执行中每 15s 续期（心跳）
- 任务完成/退出：DEL task_lock（Lua 脚本原子删除）
- 防止同一任务被多个 Worker 同时执行
```

### 14. Worker 心跳 & 僵尸任务恢复
```
- Worker 每 10s：UPDATE tasks SET worker_heartbeat=NOW()
- 监控定时任务（每 60s）：
    SELECT tasks WHERE status=RUNNING AND heartbeat < NOW()-60s
    → 重新入队，UPDATE tasks(PENDING)
- 处理 Worker 进程崩溃导致的任务卡死
```

### 15. 优雅退出（Graceful Shutdown）
```
- 捕获 SIGTERM 信号
- 停止从队列取新任务
- 等当前步骤执行完，写入 Checkpoint
- UPDATE tasks(PAUSED, paused_reason=worker_shutdown)
- 释放分布式锁，进程退出
- 新 Worker 启动时扫描 PAUSED 任务重新入队
```

### 16. HITL 超时处理
```
- APScheduler 定时任务（每分钟）
- 扫描 hitl_requests WHERE status=PENDING AND expires_at < NOW()
- 按 default_action 处理：cancel（任务失败）or proceed（默认选项继续）
```

### 17. Redis Stream 维护
```
- XADD 加 MAXLEN ~ 10000，防止 Stream 无限增长
- 监控 Stream 积压数量（超过阈值告警）
```

**P2 完成标志**：
```
✅ Worker 崩溃，60s 内任务自动恢复
✅ 服务升级时，任务优雅暂停，重启后继续
✅ HITL 超时自动处理，不需要人工干预
✅ 两个 Worker 不会同时执行同一任务
```

## P3｜生产准入（第四阶段）

> 目标：可以对外提供服务，有基本的安全和可观测性

### 18. 限流与配额控制
```
- RateLimiter Middleware（基于 Redis 计数器）
    每用户每分钟最多 N 次请求
- 并发任务数限制
    创建任务前检查：SELECT COUNT WHERE user_id AND status IN(PENDING,RUNNING)
    超限返回 429，附带 retry_after
- Token 配额（月度）
    任务完成后累加 token_used_this_month（Mock 阶段可跳过）
```

### 19. 结构化日志
```
- structlog 全局配置（JSON 格式输出）
- 每个 Request 绑定 request_id
- Worker 每个任务绑定 task_id、worker_id
- 关键事件日志：任务创建/开始/完成/失败/HITL/恢复
- 错误日志包含完整 traceback
```

### 20. 统一错误处理
```
- FastAPI Exception Handler
- 领域异常 → 标准 HTTP 错误码映射
- 生产环境不暴露内部错误详情
- 错误响应格式统一：
  { "code": "TASK_NOT_FOUND", "message": "...", "request_id": "..." }
```

### 21. 数据库迁移规范
```
- Alembic 迁移文件纳入版本控制
- 禁止直接修改数据库，所有变更通过 migration
- CI 流程自动运行 alembic upgrade head
```

### 22. 健康检查接口
```
- GET /health（存活检查）
- GET /health/ready（就绪检查：DB 连通 + Redis 连通）
- 用于 Docker / K8s 的 liveness/readiness probe
```

**P3 完成标志**：
```
✅ 单用户滥用不影响其他用户
✅ 日志可以按 task_id / user_id 过滤排查问题
✅ 所有错误有统一响应格式
✅ 部署流程有自动迁移
```

## P4｜后期增强（按需）

> 目标：接入真实 LLM，提升产品体验

### 23. 接入真实 LLM
```
- 实现 LlmAgentExecutor（实现 AgentExecutor 接口）
- 环境变量 AGENT_MODE=llm 切换
- LLM 调用封装（重试、超时、错误处理）
- Token 消耗统计写入数据库
```

### 24. 多优先级队列
```
- Redis Stream 按 priority 分为多个队列
  task_queue:high / task_queue:normal / task_queue:low
- Worker 优先消费高优先级队列
- Pro 用户任务进高优先级
```

### 25. 任务完成通知
```
- 任务完成时发站内通知（INSERT notifications 表）
- 可选：发邮件（含直接查看链接）
- HITL 触发时同样通知用户
```

### 26. 监控指标接入
```
- Prometheus metrics 接口（任务数量、执行时长、失败率、队列积压）
- Grafana 看板
- 关键指标告警（错误率超阈值、队列积压超阈值）
```

## 优先级总览

```
阶段     功能数   核心目标                    预计工作量
─────────────────────────────────────────────────────
P0       7个     整条链路跑通（Mock 模式）      大
P1       5个     功能完整（断点/HITL/取消）     中
P2       5个     异常可靠性（崩溃自动恢复）      中
P3       5个     生产准入（安全/日志/监控）      小
P4       4个     增强（真实 LLM / 通知）        按需
─────────────────────────────────────────────────────

建议节奏：
  P0 打通 → 联调前端 → P1 完善 → P2 加固 → P3 准入 → 上线 → P4 迭代
```
