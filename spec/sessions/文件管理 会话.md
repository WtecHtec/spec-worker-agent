### 一、 为什么必须新建文件表？

如果不建表，系统将面临以下问题：
- **查询代价高/脆弱**：每次前端要看文件列表，要么实时去沙箱执行 `ls` 遍历文件系统（沙箱挂掉或休眠就无法查看），要么扫描历史消息解析 Tool Call 的 payload（低效且极不可靠）。
- **权限与归属缺失**：无法快速按 `user_id` / `session_id` 做鉴权过滤和分页。
- **状态与生命周期无法追踪**：无法记录文件体积（size）、MIME 类型、最后修改时间、是否已被删除等元数据。

#### 建议的表结构设计（概念模型）

```text
Table: files (或 session_files)
────────────────────────────────────────────────────────────────
- id            : UUID (主键)
- session_id    : UUID (外键 -> sessions.id，支持级联/索引)
- user_id       : UUID (外键 -> users.id，数据所有权鉴权)
- task_id       : UUID (外键 -> tasks.id，可选，追溯是由哪个任务步骤生成的)
- file_name     : String (显示名称，如 "analysis_report.html")
- file_path     : String (沙箱/工作区内的逻辑相对路径，如 "reports/2026/analysis_report.html")
- file_size     : BigInteger (字节数，如 1048576)
- mime_type     : String (如 "text/html", "image/png", "application/pdf")
- storage_type  : String (默认 "sandbox"，未来可扩展 "s3", "minio", "local")
- storage_key   : String (在存储后端的定位标识/相对路径)
- is_deleted    : Boolean (软删除标记)
- created_at    : DateTime
- updated_at    : DateTime
```

### 二、 沙箱地址动态部署与文件访问解耦设计

#### 1. 核心痛点与风险
* **环境不固定**：沙箱可能部署在不同机器、容器动态漂移、或者分内网/公网 IP。
* **安全与越权漏洞**：沙箱内部服务通常是无状态、无复杂权限系统的。如果将沙箱直链暴露给前端用户，容易导致**未授权跨租户访问**沙箱其他文件。
* **链路迁移困难**：一旦沙箱迁移或更换域名，历史库里的所有绝对 URL 瞬间失效。

---

#### 2. 推荐方案：后端统一反向代理（BFF / Proxy Stream）

**原则：沙箱隐藏在内网 VPC 中，前端只与业务 Backend API 交互。**

```
+---------------+                    +----------------+                    +-----------------+
| 前端 Web 页面  | --- 1. 请求文件 ---> |  业务后端服务   | --- 3. 内部获取 ---> |   沙箱服务      |
| (用户浏览器)   | <--- 4. 流式响应 --- | (鉴权 + 路由解析) | <--- 4. 返回流数据 - | (VPC/内网无公网) |
+---------------+                    +----------------+                    +-----------------+
        |                                    |
        | 2. GET /api/v1/sessions/{s_id}/files/{file_id}/raw
        |    (携带用户 Token，后端进行严格鉴权)
```

##### 具体工作流程：
1. **入库阶段（Agent 写入文件时）**：
   - Agent 执行写文件工具（`sandbox_write_file`）成功后，后端截获操作。
   - 数据库插入/更新 `files` 记录，仅存储**相对路径**（`file_path: "dist/index.html"`）和元数据。
2. **列表查询阶段**：
   - 前端请求 `GET /api/v1/sessions/{session_id}/files`。
   - 后端返回文件列表，其中的下载/预览链接为统一的后端 API 格式，例如：
     - 下载：`/api/v1/sessions/{session_id}/files/{file_id}/download`
     - 预览/Raw：`/api/v1/sessions/{session_id}/files/{file_id}/preview`
3. **文件读取/预览阶段**：
   - 前端点击链接或用 `<iframe>` 预览文件。
   - 业务后端收到请求后：
     1. 验证当前登录用户是否拥有该 `session` 的查看权限；
     2. 查询 `files` 表得到该文件在沙箱中的 `file_path`；
     3. 后端读取配置中**当前生效的沙箱地址**（环境变量 `SANDBOX_URL`），在内网请求沙箱文件 API；
     4. 将沙箱返回的文件流（`StreamingResponse`）透传给前端，并设置正确的 `Content-Type` 和缓存控制头。

##### 该方案的优势：
* **彻底解耦**：沙箱 IP、域名、端口随意变动，数据库无需任何修改。
* **极致安全**：沙箱完全不暴露公网，所有文件访问必经业务系统的身份认证与权限校验（防横向越权）。
* **格式平滑升级**：如果未来沙箱任务结束后，系统将重要文件转存归档到 S3/OSS，前端访问的 API 链接完全不变，只需后端切换内部读取策略即可。

### 三、 “前端页面可以配置访问域名” 的架构落地方案

关于“配置访问域名”，通常有两种业务诉求，我们提供兼顾这两种场景的灵活设计：

#### 场景 1：前端配置系统后端 API / 网关的基础域名（Base URL）
* **背景**：前端部署在独立域名（或本地开发），后端 API 和沙箱代理部署在另一台服务器。
* **设计**：
  - 后端返回的 `preview_path` 和 `download_path` 均为**相对路径**（如 `/api/v1/sessions/.../files/.../preview`）。
  - 前端在全局配置/环境变量（如 `NEXT_PUBLIC_API_URL` 或 Web 界面设置里的 `apiBaseUrl`）中指定后端域名。
  - 前端渲染时动态拼接：`${customApiDomain}${file.preview_path}`。
  - **优势**：所有流量走后端安全代理，沙箱完全不暴露，权限完全受控。

#### 场景 2：直接配置「沙箱公网访问域名 / 外部 Web 预览域名」
* **背景**：如果某些场景下用户希望前端直接绕过后端，直连沙箱服务（例如沙箱独立部署在公网，或者支持通过泛域名直接访问 Web 页面，如 `https://sandbox.yourcompany.com`）。
* **设计**：
  - **后端返回逻辑路径**（`file_path: "dist/dashboard.html"`）。
  - **前端设置中心**提供配置项：`Sandbox Public Host / 沙箱公网访问地址`（可存 LocalStorage 或用户偏好配置）。
  - 前端提供模式切换：
    - **代理访问模式（默认）**：`${apiHost}/api/v1/sessions/{session_id}/files/{file_id}/preview`
    - **沙箱直连模式**：`${userConfiguredSandboxHost}/fs/raw?path=${file.file_path}`（或根据自定义规则拼装）。
